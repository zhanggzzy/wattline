## Context

历史分析已经有按机器或来源准备的临时 SQLite 和日期筛选接口。日常维护先将原始样本压实到本地 warm 表，再发布 gzip 并删除已导出的 warm 行。准备分析和维护共享归档锁。

## Decisions

- 在现有归档锁内构建完整的分析快照。读取已发布 gzip 后，通过一个只读 SQLite 事务读取所选来源的两个本地层。当前作业继续使用已准备的样本，归档轮转后也能一致地查询该快照。
- 在同一个临时表中按来源与毫秒时间去重。重复记录以 hot、warm、cold 的顺序优先选用。warm 表的 GPU generation 从现有字典恢复，保持采集边界。三层使用同一来源和 boot 资格规则，保留失败样本和图表中断。
- 从合并结果计算日期边界，先按起止时间选取记录，再使用已有降采样与多来源合成逻辑处理整段数据。这样跨存储层的同一个时间桶仍只产生一个点。
- 压缩字节继续驱动解压期间的进度。只有全部本地样本也暂存成功才报告 100%。失败沿用重试入口。空作业支持再次打开后重新读取，已准备的作业按现有闲置时间回收。

## Risks / Trade-offs

临时空间额外保存每个选定来源的本地历史，且分析显示准备时的快照。使用数据库游标逐条暂存，沿用原来的闲置、删除与关闭清理流程；分析时的占用随该机器的历史量变化。继续使用现有 API 参数、存储格式和 SQLite 结构，升级与回退无需迁移。
